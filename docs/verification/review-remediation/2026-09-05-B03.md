## Contract and observed behavior

| Scenario                | Observed result                                                                                                                                                                                                                                                                                                                                                                                |
| ----------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Request bound           | The strict request defaults `waitMs` to 10,000, accepts 0 through 30,000, and rejects values outside that range.                                                                                                                                                                                                                                                                               |
| Result meaning          | The result contains only `executionId`, `executionState`, and `completed`. `completed=true` means any observed terminal state, including FAILED, INTERRUPTED, and UNKNOWN; it does not mean success. The canonical response schema rejects contradictory state/boolean pairs.                                                                                                                  |
| Immediate snapshot      | `waitMs=0` returned RUNNING without allocating an Application timer or Abort listener. An already-aborted signal rejected with `AbortError` and also allocated neither resource.                                                                                                                                                                                                               |
| Timeout                 | One injected Application timer represented the full wait budget. Advancing virtual time to 9,999 ms did not settle the default wait; advancing one more millisecond returned the current RUNNING snapshot and removed the timer/listener. Timeout did not reject the Execution or synthesize failure.                                                                                          |
| Independent waiters     | Cancelling one of two concurrent waiters removed only its timer/listener. The surviving waiter received the real COMPLETED snapshot and removed its own resources. No Control write was emitted.                                                                                                                                                                                               |
| Failure settlement      | Both shared-completion resolve and reject are notification edges only. An accepted-write executor failure made the Execution UNKNOWN, while v2 resolved `{completed:true, executionState:"UNKNOWN"}` rather than propagating the completion rejection as a wait failure.                                                                                                                       |
| Synchronous failure     | An injected scheduler allocation failure rejected the observer and removed the registered Abort listener/waiter; the later shared completion remained usable. Unknown Execution returned `EXECUTION_NOT_FOUND` with no timer.                                                                                                                                                                  |
| RPC disconnect          | A raw Runtime RPC socket disconnect aborted the server request. A Unix client AbortSignal closed its request and reached the same owner waiter. Backend `RUNTIME_UNAVAILABLE` remained an error rather than `completed:false`.                                                                                                                                                                 |
| Router budget           | Router resolved the exact durable Execution route once, invoked the owner once with the same request and AbortSignal, and added no business wait timer. Missing Execution remained `EXECUTION_NOT_FOUND`; an owner business outage remained `RUNTIME_UNAVAILABLE`. Client and owner transport guards run concurrently around the single Application budget rather than serially restarting it. |
| Legacy compatibility    | Existing RPC `execution.wait` and MCP `execution_wait` shapes are unchanged. Its MCP description directs new callers to the bounded v2 tool.                                                                                                                                                                                                                                                   |
| Real timeout and output | A real zsh fixture continuously printed output. MCP `waitMs=0` and a later 100 ms wait both returned RUNNING; timeout did not stop output or the process.                                                                                                                                                                                                                                      |
| Real cancellation       | The official MCP client aborted one 30-second v2 request. A following `execution_get` observed the same Execution still RUNNING. No Control tool was invoked; the same Execution later completed normally and a new v2 wait returned `{completed:true, executionState:"COMPLETED"}`.                                                                                                           |
| Real default            | A separate real `sleep 0.1` omitted `waitMs`; MCP applied the 10-second default and returned the observed COMPLETED terminal snapshot.                                                                                                                                                                                                                                                         |

The Unix client keeps a fixed five-second local transport-settlement backstop beyond the parsed
Application wait budget. Through a Router, the outer and owner backstops start around the same
single forwarded wait; neither changes Execution state or starts a second Application wait.

## Evidence level and limits

Result: PASS at L2 for B03. L1 covers canonical bounds and cross-field invariants, injected virtual
time, every waiter cleanup path, independent cancellation, completion rejection, exact Router
forwarding, grant/capability wiring, unknown target and backend-outage classification. L2 covers a
real daemon-owned PTY/zsh, continuous output, default and timeout snapshots, official MCP
cancellation, post-cancel RUNNING observation, and later normal completion of the same Execution.

This is not L3: no browser Human Console plus external Agent workflow ran. It is not L4: no soak,
high-cardinality waiter pressure, host/network partition, rolling mixed-version owner fleet,
multi-host, Linux, or Windows/ConPTY exercise ran. B03 does not add durable waiting across owner
restart, a user deadline, automatic Control, B04 observation composition, B06 durable observation
recovery, or B07 global in-memory retention budgets.
