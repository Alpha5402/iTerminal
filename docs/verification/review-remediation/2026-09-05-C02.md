## Implemented boundary

While a Session is RUNNING, the main terminal area shows `Line input` / `Raw keys` and the exact
Session id, generation and Execution id. Line input is the default. READY still shows only the
command editor; C02 adds no Tab handler or shell-completion claim there.

Raw mode is browser-memory state armed for one exact target. Selecting it does not focus the
terminal automatically. The xterm must have explicit focus at both key capture and dispatch. Each
pending batch freezes its target and is rechecked before and after Human Guard acquisition. Blur,
Session selection, execution change, protected input, or any mismatch cancels/drops the batch with
visible `was not sent` wording; it is never posted to an old background Session. Raw controls are
also fail-closed against the current armed/focused target. A separately constructed stale HTTP
request proves the Application rejects an old Execution with `EXECUTION_CHANGED` and records no
Action.

Raw Enter, Tab, arrow escape sequences and printable/Unicode text use the existing Input Action;
exact Ctrl-C, Ctrl-D, Ctrl-Z and Escape use the existing Control Action. NUL and empty browser key
batches are classified unsupported and visibly not sent. There is no adapter/PTY direct-write
path. During active protected input, normal data does not enter raw input; the existing focused
Ctrl-C/Ctrl-D Control path remains available without depending on a raw target. Secret text stays
on the existing transient protected-input path.

Switching either direction never submits or clears a local draft. A line-mode empty Enter produces
an instruction to select Raw keys, focus the terminal, and press Enter; the `lineInput` contract was
not weakened with an empty-string special case. Switching Session deliberately resets raw even if
the Human later returns to the same still-running Execution. This conservative choice avoids an
unintended key send and is stated in the UI; it does not claim restoration of a raw choice.

## Evidence level and limits

Result: PASS at L3 for the scoped C02 programs and paths. L1 covers classification, complete target
matching and fail-closed batch admission. L2/L3 cover real PostgreSQL Actions, daemon-owned
PTY/Shell, real Console HTTP/WebSocket, browser focus and Session transitions, and official MCP
Agent contention on the same Execution.

This is not a universal terminal-emulation or all-TUI claim. Programs actually exercised were
Python 3's basic REPL, a Node readline loop and one Node raw-mode alternate-screen menu. Physical
macOS/Windows/Linux IME composition, readline libraries with application cursor mode, Vim/Neovim,
Emacs, tmux, curses applications, mouse protocols, paste pressure, cross-browser behavior,
ConPTY/Windows, long soak and hostile key-fuzzing were not tested. Therefore the result is L3, not
L4.
