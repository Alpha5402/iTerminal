## Contract and observed behavior

| Scenario           | Observed result                                                                                                                                                                                                                                                                                                                                                                    |
| ------------------ | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Source selection   | `ITERM_CONSOLE_CREDENTIAL_FILE` is an explicit absolute server-side path and is mutually exclusive with inline `ITERM_RPC_GRANT`. Inline authorization remains accepted. The Console file uses a strict Console-specific envelope rather than the MCP `mcpServers` envelope.                                                                                                       |
| Private read       | Console and MCP use the same bounded open/stat/read implementation: no final symlink following, regular same-user file, no group/other permissions and at most 64 KiB. No prior token is cached.                                                                                                                                                                                   |
| Replacement        | A live Console read an initial valid grant, then an atomically replaced grant without restart. The Runtime clock was advanced past the first grant's expiry; the next bootstrap still succeeded, proving it used the replacement rather than a cached first token. The existing MCP stdio bridge also accepted an operator replacement without process restart.                    |
| In-flight snapshot | A Runtime RPC request was held inside the gateway after authenticating its first provider result. The provider selection and Runtime clock were then changed so that first grant was expired. The held request completed with its request-start authorization; the next request invoked the provider once more and used the new grant.                                             |
| Fixed authority    | Console grants must declare the fixed paired-prefix Human Console Actor and canonical Human capabilities; MCP grants must declare the configured exact Agent. After the first valid read, audience and canonical operation list are pinned. Actor or operation-scope drift is rejected before RPC dispatch. File data never replaces the Console cookie Actor or enters bootstrap. |
| Fail closed        | Missing/transient source reads returned retryable `RUNTIME_UNAVAILABLE`; insecure permissions, malformed JSON/token, expired grants, socket/Actor mismatch and scope drift returned `POLICY_DENIED`. Responses/errors contained neither credential bytes nor file paths. Restoring a valid file made the next request work; no stale grant fallback occurred.                      |
| PTY continuity     | Across Console grant replacement, the same Session id/generation remained `READY`, exactly one `session.shell_ready` fact remained, and its observed `shellPid` was unchanged. No Session rebuild or PTY replacement was used to recover authorization.                                                                                                                            |

## Evidence level and limits

Result: PASS at L2 for the scoped D03 behavior. L1 covers source selection, strict file shape and
permissions, fixed Actor/operation scope, error classification, redaction, provider call count and
in-flight snapshot semantics. L2 covers replacement through a real Console HTTP server,
authenticated Runtime daemon, Unix socket and zsh PTY, plus the existing official MCP stdio
credential replacement path. The unchanged shell PID is observed from the Runtime's
`session.shell_ready` fact rather than inferred from Session status.

This is not automatic renewal: no issuer or signing key was added to Console/MCP and no expiry
scheduler ran. It is not a browser-driven L3 workflow, multi-owner deployment, long-duration soak,
same-user hostile-process test, Linux run or Windows/ConPTY run. A forged but structurally valid
first file grant can still cause a local denial of service by establishing an unusable pinned
scope; Runtime signature verification prevents authority gain, and operator recovery may require
restarting that client if the intended scope differs. Supervisor-managed same-scope renewal is a
later remediation card.
