## State and truth boundary

The reducer has explicit `idle`, `submitting`, `uncertain`, `accepted` and `rejected` states. An
active identity freezes the exact Session id, generation, optional target Execution id, draft
revision, request payload, idempotency key, and known Action id. The payload and identity live only
in React memory: they are not written to local/session storage, command history or logs. Secret
input never enters this reducer. A `beforeunload` warning exists only for `submitting` and
`uncertain`; the UI explicitly says that leaving or refreshing loses the lookup identity and does
not recover or retry the submission.

`accepted` means only that the Action returned by the write response or exact A06 lookup is an
accepted/found server fact. The banner renders the actual Action status and, when returned, the
actual Execution status, followed by an explicit statement that this is not proof the program
handled the input or that execution succeeded. `UNKNOWN` and `FAILED` therefore remain their
actual server statuses; the UI does not translate them to success.

Only structured Console error codes proven to precede terminal write admission are rendered as
definite `rejected`: validation, policy/approval, rate/backpressure, PTY contention, sensitive or
guarded interaction, freshness, Session/generation and target-Execution failures. Transport,
parsing, generic HTTP/runtime availability and `DELIVERY_UNKNOWN` failures remain `uncertain`.
`IDEMPOTENCY_KEY_REUSED` also remains uncertain because an older Action under that key can exist and
must be reconciled rather than hidden by a replacement identity.

While an intent is pending, both READY and foreground Enter return before invoking the lazy
idempotency-key factory. Foreground interaction/input-context reads occur before intent creation;
their failure cannot mutate an older accepted/rejected card. Once an intent exists, any late write
or lookup result must match its Session, generation and key. Draft clearing additionally requires
the original draft revision and foreground Execution scope, so text typed while waiting or a
different Session/generation is not cleared.

## Real lost-response browser scenario

The extended shared-path test runs a real foreground readline program through a daemon-owned PTY,
keeps an official MCP Agent connected, and submits `uncertain-line` from the Browser Console. The
Playwright route handler calls `route.fetch()` first, allowing the real `/input` request to finish
and write once, then aborts delivery of that response to the page. This is a response-loss fixture,
not a request-before-server abort.

Observed assertions:

| Scenario                          | Result                                                                                                                                                                                                                                                         |
| --------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Lost response then repeated Enter | Browser observed exactly one `/input` POST; repeated Enter created/adopted no replacement identity and sent no second write.                                                                                                                                   |
| Side effect cardinality           | The terminal showed exactly one `ACK:uncertain-line`; PostgreSQL contained exactly one Action for the frozen idempotency key.                                                                                                                                  |
| New text while waiting            | `newer local draft` remained visible through `not_found` and later `found`; the late acceptance did not clear it.                                                                                                                                              |
| Duplicate check click             | Two synchronous clicks while lookup was in flight produced one lookup. The check path issued only A06 POST lookup and no PTY write.                                                                                                                            |
| `not_found` then `found`          | The first lookup was deliberately fulfilled with the canonical A06 `not_found` envelope to exercise the UI state machine; the second continued to the real A06 route and found the already accepted Action. This is not a claim about natural database timing. |
| Definite validation rejection     | An invalid multiline foreground line was shown as `rejected`; its text remained editable, and editing created the later independent intent.                                                                                                                    |
| Actual server status              | The accepted banner displayed `actual status DELIVERED` and the explicit no-execution-success disclaimer.                                                                                                                                                      |
| Secret and navigation boundary    | The existing real secret-input test remained green, and reducer tests reject late/cross Session or generation settlements. The submission banner does not intercept unrelated page controls.                                                                   |

## Evidence level and limits

Result: PASS at L3 for C01. L1 covers reducer identities, transitions, freshness and rejection
classification. L2 covers exact durable lookup and the real dropped HTTP Execute response without
duplicate effect. L3 covers a real production-built Browser Console, HTTP/WebSocket, official MCP
Agent, daemon-owned PTY/Shell and PostgreSQL while the foreground Input response is lost after the
server accepts it.

This is not a cross-refresh recovery claim: version one is intentionally memory-only. It is not L4:
there was no browser crash restoration, long network partition, pressure/soak, hostile storage
inspection, multi-host, mixed-version, Linux, Windows/ConPTY or additional-browser exercise. The
synthetic first `not_found` proves the UI transition, not a naturally observed race. The product
still requires the Human to choose Check result; it never automatically replays an unknown write.
