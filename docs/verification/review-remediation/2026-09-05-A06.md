## Contract and security observations

| Scenario              | Observed result                                                                                                                                                                                                          |
| --------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| Lost response         | A real Console Execute response was dropped. POST lookup with the original cookie, Session, generation and key returned the one accepted Action/Execution; the fixture file still contained exactly one line.            |
| Request still delayed | Lookup before acceptance returned `not_found` with `mayStillBeInFlight: true` and the warning not to generate a replacement key; the same lookup returned `found` after acceptance.                                      |
| Current/durable truth | Application returned the live in-memory status first. A separate RuntimeService with an empty store recovered the completed fact from PostgreSQL.                                                                        |
| Actor isolation       | Another Console cookie, another Actor ID, and the same Actor ID with a changed principal received the same non-disclosing `not_found`; a forged Actor field in the Console body was rejected.                            |
| Grant isolation       | An exact `action.lookup` grant succeeded. A different-operation grant, a forged principal and an invalid bearer were denied before lookup dispatch and did not expose Action/Execution IDs.                              |
| Generation isolation  | The same Actor/key under another generation returned `not_found`, not the prior generation's fact.                                                                                                                       |
| Durable outage        | After closing the real PostgreSQL durability pool, a fresh Application lookup returned retryable `unavailable` with `durability_unavailable`, not `not_found`.                                                           |
| Owner routing         | Router forwarded to one exact Session owner. Missing Session returned `not_found`; ownerless/database/connection routes returned `unavailable`; `POLICY_DENIED` remained an error.                                       |
| Status truth          | `UNKNOWN` remained `UNKNOWN`; completed Execute exposed Action and Execution status; real Input and Control lookup exposed their actual `DELIVERED` status.                                                              |
| No side effect        | Lookup did not allocate an Action/Execution or sequence and did not invoke Execute/Input/Control/resize. It never returned command, input/control payload, complete Actor, capability list, request hash, path or token. |
| Retention             | Existing storage has no request-specific deletion tombstone. The protocol reserves `expired`, but this implementation never manufactures it; absence remains warned `not_found`.                                         |
| Capabilities          | Direct Runtime and Router advertise `action.lookup.v1` only after the handler exists. A targeted Router capability request remains the exact owner's feature set, never a fleet union.                                   |

The Console uses POST with a strict body despite read-only semantics so the idempotency key is not
placed in URL query logs or browser history. HTTP and MCP bind Actor from their authenticated
adapter context; no public lookup accepts Action ID, Actor or request hash as an authority.

## Failed attempts and disposition

- The first `pnpm verify` stopped on one unused fixture parameter. After removing it, the next run
  stopped because that file needed Prettier. Both local authoring defects were fixed.
- A full verify with PostgreSQL and the default macOS temporary directory reported 7 failures in
  4 existing PTY/guardian files. The concrete root error was Unix socket `listen EINVAL`; setting
  `TMPDIR=/tmp` made those exact 4 files / 13 tests pass.
- A later full verify pointed every PostgreSQL-gated file at one database and reported 2 failures
  after an existing owner-registry test left `session_creation_policies.max_requests = 1`. Those
  later tests received expected `BACKPRESSURE` from cross-file database policy pollution. This was
  not used as acceptance evidence. Each A06/card database command began from its own truncation and
  passed; the repository gate then used its normal environment-gated mode.

## Evidence level and limits

Result: PASS at L2 for A06. L1 covers canonical schemas, no-side-effect behavior, status
projection, identity/generation/grant isolation, Router classification, payload omission and
capability accuracy. L2 covers real Console HTTP response loss, official MCP stdio through Unix
RPC and real PTY/Shell operations, plus PostgreSQL recovery from a fresh empty-memory Application
instance and a real durability-object outage.

This is not L3 because no browser-driven shared Human Console plus external Agent workflow ran.
It is not L4: there was no multi-host, TLS, pressure/soak, rolling mixed-version, Linux, Windows or
ConPTY exercise. No request-specific retention tombstone exists, so `expired` remains unobserved
and intentionally unreported. No admission cancellation/rejection protocol was added, and
`not_found` never authorizes automatic retry under a new key.
