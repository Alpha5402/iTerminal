## Implemented ordering

- Console HTTP authenticates its server-created Human Actor, enforces ingress/origin controls, and
  validates strict bounded JSON before invoking the Runtime gateway. It no longer fetches Session
  state to decide Execute READY mode or Input/Control RUNNING target freshness.
- Application serializes each mutation, flushes durable work, computes the request hash and actor
  scope, then resolves an exact replay before mutable generation, Execution, policy, or Guard
  checks. New requests continue through all current authorization and freshness checks.
- A replay hit must match the complete immutable Actor stored on the Action before either the
  original fact or a payload-conflict result can be returned. Same actor ID with a changed
  principal or stripped capabilities returns `ACTOR_IDENTITY_CONFLICT` without a PTY write.
- The same actor/key/payload returns the original Action/Execution after completion. The same key
  with changed payload returns `IDEMPOTENCY_KEY_REUSED`. A new key aimed at an old Execution returns
  `EXECUTION_CHANGED`.
- Different principals do not share an idempotency domain. In the deterministic probe, a different
  authorized principal using the same textual key created a distinct Action/Execution and a second
  executor write; it did not receive the first principal's fact.

## Real observations

| Scenario                   | Observation                                                                                                                                 |
| -------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------- |
| Lost Execute HTTP response | The client destroyed the response stream after the server produced headers; the fixture command appended exactly one `once` line.           |
| Reconciliation             | After the real zsh returned READY, resending the same cookie/key/payload returned the original Action and Execution IDs in `COMPLETED`.     |
| Duplicate side effect      | The marker remained exactly `once\n`; the Session had exactly one accepted ExecuteAction for that Console Actor.                            |
| HTTP Input replay          | A Human InputAction accepted during a Python Execution replayed after completion with the original Action ID and no second accepted Event.  |
| HTTP Control replay        | A real `SIGCONT` ControlAction replayed after completion with the original Action ID and no second accepted Event.                          |
| Invalid signed grant       | A Console using a tampered grant received generic `POLICY_DENIED`; its body contained no original Action ID, Execution ID, or fixture path. |
| New stale request          | A new idempotency key targeting the prior Execution returned `EXECUTION_CHANGED`.                                                           |

## Evidence level

Result: PASS at L2 for A04. The evidence combines deterministic Application executor-write counts
with real loopback HTTP, signed Unix Runtime RPC authentication, Runtime daemon, node-pty, and zsh.
It proves replay after mutable state changes, lost-response reconciliation, and transport grant
denial without touching a shared service or database. This is not an L3 browser/MCP shared-path or
an L4 network-fault, pressure, hostile same-user, or cross-platform claim.

## Compatibility and rollback

- Public HTTP/RPC/MCP schemas and success DTOs are unchanged. Rejected READY raw Input now exposes
  Application's `EXECUTION_CHANGED` instead of the Console preflight's `SESSION_NOT_READY`.
- Existing Console clients continue to send generation, target Execution, and idempotency key; the
  authoritative validation location changes from HTTP preflight to Application.
- Rollback restores duplicate transport decisions and makes accepted Input/Control replays fail
  after the target leaves RUNNING.

## Not covered

- PostgreSQL-backed durable replay after a full Runtime process restart was not exercised; A04 did
  not change persistence schema or admission transactions.
- The lost-response fixture discards an actual loopback HTTP response after headers; it is not a
  kernel packet-drop, proxy reset, machine crash, or network-partition test.
- No real browser, official MCP client, remote authentication, TLS, Linux, Windows/ConPTY,
  multi-host Router, high pressure, or long soak was run for A04.
- Different principals intentionally have distinct idempotency scopes. This work does not claim
  cross-principal deduplication and does not make the loopback Console a hostile multi-user system.
