## Version and feature strategy

- `protocolVersion` is the wire-compatibility generation and is currently `1`. Additive operations
  and feature names do not increment it; an incompatible wire change does.
- `buildId` is an explicit bounded startup/build identifier. Omission produces `unknown`; path-like
  and otherwise non-canonical identifiers are rejected rather than reflected.
- Feature names are bounded, sorted and duplicate-free. The schema accepts future canonical names
  so an older compatible client can ignore capabilities it does not know.
- A direct daemon currently advertises `action.execute.v1`, `action.input.v1`, and
  `runtime.capabilities.v1`. The Router advertises only `runtime.capabilities.v1` and
  `runtime.owner-capabilities.v1` for itself. A Router request with `sessionId` resolves and returns
  that exact live owner's response; it does not union owner features.
- Console performs a fresh handshake on every bootstrap. Matching version is `compatible`, a
  different version is `incompatible`, and a missing method or the old RPC's exact unsupported
  operation response is `legacy`. Other authentication, validation and availability failures are
  not downgraded.

## Compatibility and rollback

- Existing RPC operations and Console fields remain additive. Old clients can continue old
  operations and ignore the new bootstrap field or MCP tool.
- New Console clients preserve old endpoints when an old service explicitly lacks the handshake;
  they do not infer capability support from this checkout.
- Runtime RPC grants for MCP and Console local credentials add the read-only operation. Existing
  grants without it retain their old permissions but cannot negotiate capabilities.
- Rollback removes negotiation and canonical schema reuse; it does not rewrite Sessions, Actions,
  database facts or live PTYs.

## Not covered

- No PostgreSQL-backed Router process, multi-host deployment, rolling binary replacement, remote
  authentication, TLS, browser automation, Linux, Windows/ConPTY, pressure or soak scenario ran.
- Router mixed-owner behavior used deterministic in-process route/client fixtures rather than a
  real PostgreSQL registry with two daemon processes.
- Build provenance/signing is not introduced. `buildId` is only a safe explicit identifier or
  `unknown`, not an attestation.
- Feature negotiation does not migrate every historical DTO and does not advertise later review
  cards before their implementations land.
