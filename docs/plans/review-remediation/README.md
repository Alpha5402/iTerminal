# iTerminal 审阅整改执行计划

日期：2026-09-05。状态：执行中。适用对象：按单张任务卡工作的 Sol / Luna。

本计划把本轮审阅的 28 项意见转成 36 张任务卡。它规定目标行为和验证方法，不要求执行模型再次进行全仓架构审阅，也不把“模型能力不足”当成已证实的根因。优先修正真实语义错误、不可恢复的操作体验和 Agent 观察成本，再优化结构。

调度更新：遵循 [小批次调度与工作树恢复](DISPATCH.md)，最多同时两个开发 worktree 加一个集成 worktree；等待任务只留在队列，不提前创建。旧执行提示词中的“不提交”受用户后续 commit/push 授权覆盖，但 main 只由集成工作统一推送。

## 使用方法

1. 新执行会话读取仓库 `AGENTS.md`、本文件、指定任务卡；涉及运行语义时，再读取 `TODO.md`、`docs/TERMINOLOGY.md`、ADR 索引、任务相关 ADR 和最近相关验证记录。后续卡只补读变化与相关文档。
2. 每次只做一张卡。优先按下表顺序；依赖没完成就不做依赖任务。不要把整个阶段交给 Luna 一次执行。
3. 所有卡默认是独立、可审阅的增量。表中的模型是工作分配建议，不是性能保证。标记 Sol 的卡涉及状态、并发或跨层契约；Luna 不应自行扩大这些卡。
4. 先定位卡中的入口，再沿直接调用链阅读；不要默认扫描所有源码、重跑所有历史集成测试或读取所有历史验证记录。
5. 完成后更新本索引的状态格，新增对应验证记录；状态使用 `未开始 / 进行中 / 已实现待验证 / 已验收 / 阻塞`。仅运行通过且满足卡中要求，才能写“已验收”。
6. 使用 [执行提示词](EXECUTOR-PROMPT.md) 交接。下一次只需传任务 ID、上一次交付摘要和必要证据。

## 基线与修改边界

- 审阅基于 HEAD `138dfb6` 加当时未提交工作区；已有 57 个修改或未跟踪条目，其中包括本地行草稿、credential-file、终端回复等新实现。这个数字只描述计划编写时的基线。
- 执行前重新读 `git status --short`，保护已有工作。不自动 reset、stash、checkout、全仓格式化、提交或推送。不以 HEAD 文件覆盖当前工作文件。
- 本次仅新增计划文档，没有实施任何运行时代码修改。原 `TODO.md` 和历史验证记录没有被重写。
- 卡中路径均相对仓库根目录；标记“新增”的文件或接口是计划产物，不是已经存在的能力。源码行号可能移动，以符号为准。
- 不控制用户已有会话，不重启用户服务，不向现有终端发送测试命令。测试创建独立临时目录、独立 owner/socket、独立会话；清理只能影响该测试的资源。
- PostgreSQL 集成测试只能使用隔离测试实例中的 `iterminal_test`。现有部分测试会 TRUNCATE；仅数据库名字正确不足以证明它与用户运行环境隔离。

## 已固定的实施决策

1. **保留现有核心约束。** 一个 generation 一个 PTY/Shell；Application 串行决定写入；一个活动 Execute；精确 generation/execution；合并输出；UNKNOWN 不重放；失去 PTY 不原地复活。
2. **等待与执行寿命分开。** 默认执行没有隐式 24 小时寿命上限。观察超时结束等待，不结束进程。不在整改中引入作业调度器或新 deadline 子系统。
3. **只缩小已知故障范围。** 可证明属于单个 session 的 fencing 失败只隔离该 session；owner 丢失、数据库状态不明仍保持既有安全处置。不引入“断开数据库后继续写 PTY”。
4. **兼容迁移。** 现有公开工具与响应保留；新的有界观察、发现和等待走有版本的新契约，经 capabilities 暴露。不要为了降噪直接删旧工具或改变旧工具返回结构。
5. **屏幕保真沿现有投影做。** 复用 `TerminalScreenCell` 与现有 headless screen，先保留颜色/属性，再加滚动历史。此轮不新增第二条原始 VT 广播链路，不复制 PTY，不重放原始 OSC。
6. **不确定提交先保留身份。** 同一用户意图冻结 payload/key/目标；网络失败不能生成新 key 重试。`NOT_FOUND` 只是一次查询结果，不证明原请求永远不会抵达。
7. **先提供持久事实查询，再淘汰缓存。** 禁止用 LRU 删除唯一幂等记录后让同 key 重新执行。过期 key 必须拒绝或保留防重放依据；内存模式达到上限可拒绝新写入，不能遗忘后重执行。
8. **凭据更新不重建会话。** 复用私有 credential-file 路径；同身份、同作用域刷新，原子替换。不把 token 放到页面、URL、日志或验证报告。
9. **有界输出默认值是新设计预算。** 输出默认 8 KiB、单次最多 64 KiB；新等待默认 10 秒、最多 30 秒；新分页默认 50 项、最多 200 项。它们不是现有性能测量结果。响应标明截断、gap、过期和下一游标；不能用静默丢弃满足预算。
10. **不以确认按钮制造事实。** 用户承认“不确定”不等于程序输入缓冲区已知。C03 只提供解释和现有安全操作；自动清空、强行重置为 known、空白回车恢复均不在范围。

## 通用完成标准

每张实现卡都须满足下面条款；卡内列出的验证是额外要求。

- 交付有实现、失败路径测试、兼容性说明和精确验证命令。需要 ADR 时先新增 ADR 草稿再实现，同一交付中确认最终决策；编号从当前目录分配，不能假定 0067 空闲。
- 所有新增公开请求都必须有 schema、认证/授权映射、RPC 路由、必要的 router 转发、MCP/HTTP 消费方契约测试。只改 server handler 不算端到端完成。
- 新错误优先复用现有错误体系；新增错误在 domain、协议和使用方同步。不得把鉴权失败、过期、未知副作用都压成“重试”。
- 每张实现卡运行 `pnpm typecheck`、该卡定向测试、`git diff --check`。对所改文件运行 Prettier 检查。纯文档卡无需运行 PTY/PG 测试。
- 阶段收尾或用户要求 commit/push 收尾前运行 `pnpm verify` 和对应真实场景。过程中不因每处小改动重复全量 verify。已有脏文件导致的失败单独报告，不替用户修无关改动。
- 验证写入新增 `docs/verification/review-remediation/<日期>-<任务ID>.md`，沿用仓库文档检查要求；包含 revision/工作区差异范围、环境、命令、pass/fail/skip、真实观察、未覆盖项。不要在历史证据上改通过数。
- L0 是静态设计；L1 是单元/契约；L2 是真实 PTY/Shell/PG；L3 是真实 Console 与 MCP 共用 runtime；L4 必须说明具体故障注入/压力/平台范围。一次故障注入不代表完成全部 L4。
- 不写“全部安全”“完全兼容 TUI”“长期稳定”之类超出证据的结论。不生成无意义的逐行实现镜像测试。
